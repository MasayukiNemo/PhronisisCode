# deep_thought.md — クイズ リッチWeb UI版

## 起動理由

UI手段の選択が本タスクの核心（ユーザーがKaiに一任）。設計分岐が複数あり発散が必要。創作・転換の局面。

## 問い

「グラフィカルでリッチ」を、既存の制約（追加依存なし・stdlib・出題ロジック再利用・quota作法維持）の中で最大化するには何が最適か。

## 発散した選択肢

### A. tkinter Canvas 自前描画（既存GUIの延長）
- 追加依存なし・exe同梱容易。既存quiz_gui.pyの延長線上。
- しかし「リッチ」の到達点が低い。グラデーション・blur・滑らかなアニメ・レスポンシブは自前実装の苦労が大きく、品質が頭打ち。
- 「苦労はできるだけ逃げろ。逃げ切れない苦労が本当の苦労」。ここは逃げていい苦労。

### B. Pygame / ゲームエンジン
- 表現力は高いが追加依存。既存の「実行時追加依存なし」作法を破る。exeサイズも増える。
- クイズに物理演算は不要。過剰。

### C. ローカルWeb UI（stdlib http.server + 同梱HTML/CSS/JS）
- 追加依存ゼロ。ブラウザはOS付属。CSSで真のリッチ表現（アニメ・グラデ・ガラス・confetti）が書ける。
- ロジックはPython側に閉じ、thin APIでcore.fetch_questionsを呼ぶ。二重実装なし。
- 懸念はサーバの安全性・プロセス管理・ブラウザ起動の堅牢性。これは設計で潰せる。

### D. 外部サーバ / SaaS
- 過剰。ローカル完結の要件に反する。

## 収束

C。理由は「リッチさの到達点」と「追加依存ゼロ」の両立。Aは妥協、Bは依存追加、Dは過剰。
Cの懸念（セキュリティ・堅牢性）は、127.0.0.1バインド＋ワンタイムトークン＋Host/Origin検証＋
ポートフォールバック＋確実なシャットダウンで解消する。

## リッチさの具体定義（受け入れ時の主観を排すため）

1. 動く背景（CSSアニメーションのグラデーション/オーロラ）がある
2. ガラス調（透過+ぼかし）のカードで情報を提示する
3. 選択肢にホバー/選択/正誤の状態遷移アニメがある
4. 出題切替にトランジションがある
5. 進捗（問数）が視覚化される
6. 結果画面にスコア演出（リング/カウントアップ/高得点時confetti）がある
7. 生成待ちにアニメーションインジケータと経過/目安表示がある

質疑: 「リッチ＝装飾過多」ではない。情報の可読性を損なわず、状態が一目で伝わること。装飾は状態伝達に奉仕させる。

## リスク認識（先回り）

- ブラウザ自動オープン失敗 → URLをコンソールに必ず出す
- ポート衝突 → 0番バインドで空きポート取得
- 生成中の二重リクエスト → サーバ側/クライアント側でガード
- XSS（LLM生成文字列をDOMに出す） → textContent のみ使用、innerHTML禁止
- quota残取得不能時 → 既存同様「取得できず続行」だが、UIに明示
- プロセス残留 → Ctrl+Cで確実にシャットダウン。ブラウザ側にも終了導線
