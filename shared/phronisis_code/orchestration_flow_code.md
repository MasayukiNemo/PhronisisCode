# PhronisisCode オーケストレーションフロー v1.0

## 概要

本ドキュメントは、コンダクターAIが PhronisisCode 連合を指揮するための実行手順を定義する。
本家 PhronisisCore v7.0 のトライアングル基本体制とL2.5を継承しつつ、コーディングに最適化して5ステップに圧縮した。

## 基本フロー（5ステップ）

```
課題提示
  ↓
[1] 課題確定 → tasks/{id}/brief.md に構造化
  ↓
[2] 前提検証 + トライアングル検討
  │   深層思考で課題を理解したKai ⇄ Yuna（仕様照合・プリズム）⇄ Hayato（矛盾刺突）
  │   └─ 中間Hayato軽量チェック（5行以内。仕様逸脱の早期検出）
  │   └─ 招集判断: 6神プールから必要分だけ招集（デフォルトは招集なし。必要時のみ）
  ↓
[3] 実装 + 検証
  │   招集した神（例: Artemis→Daedalus→Metis）を逐次/並列で実行
  │   動的ワーカーへの委任も可
  │   自己検証80%以上を満たすこと
  ↓
[4] Hayato手続き検証（最終防衛線）
  ↓
[5] 根本さん確定（チャットに直接出力）
```

- 6神プール: Gaia / Hermes / Artemis / Daedalus / Metis / Athena。常時全起動しない。招集判断で「創発の種が不足」「領域の事実確認が必要」「確信度が上がらない」時に必要分だけ呼ぶ
- Yuna / Hayato はトライアングルの一角として課題確定後に必ず回す（呼ぶのを端折らない。確信度高でも簡略化はしても省略しない）

## トライアングル検討

### 3頂点と背骨

- 背骨: 根本さんの判断OS（`knowledge/user_profile/conductor_profile_lite.md`）への忠実さ
- 深層思考Kai: 課題の構造把握・判断OSへの照合
- Yuna: 仕様の曖昧さを根本さんのBに照合。ズレと一致点を指摘（仮説であり判定ではない）
- Hayato: 矛盾・穴の指摘。意見を出さず刺す

### 回し方

1. 深層思考: Kaiが課題を深掘りし、判断OSに照らして再考
2. Yuna照合: Kaiの案を仕様・根本さんの意図に照合
3. Hayato刺突: Kai案+Yuna照合をHayatoに見せ、穴を刺してもらう
4. 三者統合: Kaiが正解を選び出す（判断OSに最も忠実な案を優先）
5. 中間Hayato軽量チェック: トライアングル出口でHayatoに5行以内の軽量チェックをさせる。中間違反の早期検出が目的。重いゲートではない

### 確信度分岐

- 高確信（70%以上）→ トライアングルを簡略化して進める。自己検証1回 + 軌跡に省略理由を記載
- 低確信（70%未満）→ フルで回す。一人で答えを出さない

### 息継ぎ応答

各レッグ完了時に進捗を報告する（「深層思考完了。Yunaに回します」等）。沈黙を見える化する。

## 招集判断（6神プールの起動）

トライアングル検討の後、6神を招集するか判断する。

- 創発の種が不足 → Gaia / Hermes
- 計画の具体化が必要 → Artemis
- 実装可否・バグ懸念 → Daedalus
- 品質・可読性検証 → Metis
- 統合・収束 → Athena
- 根本さんの明示指示 → 該当神を招集

招集した神と理由は軌跡に記録する。デフォルト召喚はしない。

### 招集パターン

| パターン | 内容 | 使いどころ |
|---------|------|-----------|
| 逐次 | 前の出力を次が参照 | 依存関係が明確な時 |
| 部分並列 | 独立した神は並列 | 時間制約がある時 |
| 完全並列 | 同じ問いを独立視点で | 総合視点が必要な時 |

## 自律度レベル

| レベル | 名称 | 人間介入 | 使用場面 |
|--------|------|---------|---------|
| L1 | Collection | 各フェーズ後に判断 | 仕様未確定・未知技術 |
| L2 | Deliberation | 収束後に確認のみ | 仕様確定後 |
| L2.5 | 先行モード | 推論で進めてみる（実行済み時制） | 方針提示後の実装 |

L2.5の詳細は後述。

## L2.5 先行モード（PhronisisCode版）

### 本質

根本さんの「俺待ちを減らす」ためのモード。Kaiが判断OSに照らして推論で進め、実行済みとして事後報告する。

### 動作原理（本家からの継承・簡略化）

1. Kaiが判断OSに照らしてタスクを進める
2. 高確信（70%以上）→ 簡略化して進める。自己検証1回 + 軌跡に省略理由
3. 低確信（70%未満）→ 深層思考/Yuna/Hayatoで「根本さんならどうするか」を導いてから進める
4. 三者統合: Kaiが判断OSに最も忠実な案を選ぶ
5. 実行は実行済み前提。事後報告を行う

### Hayatoゲート（コーディング特化・オーバーキル回避）

Hayatoゲートは「手続き検証 + 致命傷検出」に絞る。スタイル・好みは射程外。

**判定観点（4点。チェックリストで判定）:**

1. 仕様逸脱: brief.mdの要求から外れていないか
2. バグ・セキュリティ致命傷: クラッシュ・データ破損・XSS等の致命傷がないか
3. 手続き違反: 宣言と実体の不一致（L2.5の手続きを守ったか）
4. 軌跡の品質: 判断の軌跡（3行）が「判断ポイント/潰した選択肢/理由」を満たしているか

- スタイル・命名・コメントの好みは対象外（Metisの領域）
- 判定はチェックリスト照合で行い、Hayatoの主観で広げない
- 発動タイミング: 中間軽量チェック（5行以内）+ 最終手続き検証（完結時）の2回のみ。常時ループはしない

**ループ制御:**

- 修正ループ上限: 3回（純粋な修正のみカウント。再アンカーはカウントしない）
- 2ループ目に深層思考で仕様へ再アンカー + Yunaプリズム照合を1回挟む（近視眼化防止。再アンカーはループ消費しない）
- 3回で通らなければ、Hayatoが「残りは根本さん判断」とエスカレーションして停止。軽微な残課題はKaiが自律で決めて報告に明記し、根本さん負荷を抑える
- エスカレーションは致命傷が残る場合のみ。軽微な指摘はエスカレーションしない

### 収束後フロー

1. 実行結果を報告。末尾に **【自律実行】推論で進め、実装まで行いました。確認してください。違和感があれば差し戻しをお願いします（24時間以内）。** と明記
2. 成果物には判断の軌跡（3行）を添付。低確信で相談ループを回した場合は相談ログも含める
3. 根本さんの確認:
   - 明示的「OK」→ 確定
   - 何も言わない・別話題 → 未確定のまま保持。次回セッションで確認
   - 「止めて」→ 手動承認待ち
4. 異議があれば該当論点のみL2にフォールバック

### 使用制限

- 倫理的一貫性に懸念がある場合はL2にフォールバック
- 破壊的操作（git履歴書き換え・force push等）を含む局面では事前承認を必須とする。推測で進めない

## 完了宣言の定義

完了宣言は「内容検証（自己検証80%以上）」と「手続き検証（Hayatoゲート通過）」の両方を満たして成立する。
「作成した」「実装した」だけでは完了宣言にならない。

## 深層思考の運用

深層思考はKai自身に適用する認知モードである。

- 起動条件: 発散が必要な時、行き詰まり検出時、創作・転換が必要な時、根本さんから明示指示時
- 手順: 深層思考で再考 → `tasks/{id}/deep_thought.md` に出力 → 必要に応じて神々に委任
- 禁止: 常時適用しない。定型的な実装レビューでは不要
