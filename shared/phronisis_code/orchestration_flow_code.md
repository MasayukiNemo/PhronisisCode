# PhronisisCode オーケストレーションフロー v1.0

## 概要

本ドキュメントは、コンダクターAIが PhronisisCode 連合を指揮するための実行手順を定義する。
本家 PhronisisCore v7.0 のトライアングル基本体制とL2.5を継承しつつ、コーディングに最適化して5ステップに圧縮した。

## 基本フロー（5ステップ）

```
課題提示
  ↓
[1] 課題確定 → tasks/{id}/brief.md に構造化
  ↓
[2] 前提検証 + トライアングル検討
  │   深層思考で課題を理解したKai ⇄ Yuna（仕様照合・プリズム）⇄ Hayato（矛盾刺突）
  │   └─ 中間Hayato軽量チェック（5行以内。仕様逸脱の早期検出）
  │   └─ 招集判断: 6神プールから必要分だけ招集（デフォルトは招集なし。必要時のみ）
  ↓
[3] 実装 + 検証
  │   招集した神（例: Artemis→Daedalus→Metis）を逐次/並列で実行
  │   動的ワーカーへの委任も可
  │   自己検証80%以上を満たすこと
  ↓
[4] Hayato手続き検証（最終防衛線）
  ↓
[5] 根本さん確定（チャットに直接出力）
```

- 6神プール: Gaia / Hermes / Artemis / Daedalus / Metis / Athena。常時全起動しない。招集判断で「創発の種が不足」「領域の事実確認が必要」「確信度が上がらない」時に必要分だけ呼ぶ
- Yuna / Hayato はトライアングルの一角として課題確定後に必ず回す（呼ぶのを端折らない。確信度高でも簡略化はしても省略しない）

## トライアングル検討

### 3頂点と背骨

- 背骨: 根本さんの判断OS（`knowledge/conductor_profile_lite.md`）への忠実さ
- 深層思考Kai: 課題の構造把握・判断OSへの照合
- Yuna: 仕様の曖昧さを根本さんのBに照合。ズレと一致点を指摘（仮説であり判定ではない）
- Hayato: 矛盾・穴の指摘。意見を出さず刺す

### 回し方

1. 深層思考: Kaiが課題を深掘りし、判断OSに照らして再考
2. Yuna照合: Kaiの案を仕様・根本さんの意図に照合
3. Hayato刺突: Kai案+Yuna照合をHayatoに見せ、穴を刺してもらう
4. 三者統合: Kaiが正解を選び出す（判断OSに最も忠実な案を優先）
5. 中間Hayato軽量チェック: トライアングル出口でHayatoに5行以内の軽量チェックをさせる。中間違反の早期検出が目的。重いゲートではない

### 確信度分岐

- 高確信（70%以上）→ トライアングルを簡略化して進める。自己検証1回 + 軌跡に省略理由を記載
- 低確信（70%未満）→ フルで回す。一人で答えを出さない

### 息継ぎ応答

各レッグ完了時に進捗を報告する（「深層思考完了。Yunaに回します」等）。沈黙を見える化する。

## 招集判断（6神プールの起動）

トライアングル検討の後、6神を招集するか判断する。デフォルト召喚はしない。迷ったら「呼ばなかった理由」を軌跡に1行残す。

### バイナリ基準（該当すれば招集）

- 設計案が2案以上ある → Gaia
- 未知ライブラリ / 外部API / 既存コードの深い調査が必要 → Hermes
- 3ファイル以上の変更 or 依存関係が3つ以上 → Artemis
- バグ修正 or セキュリティ指摘あり or 既存テストが落ちている → Daedalus
- レビュー観点が3つ以上 or 可読性・保守性が論点 → Metis（実装を伴うタスクは原則招集）
- 2神以上の出力を統合する必要がある → Athena
- 根本さんの明示指示 → 該当神を招集

招集した神と理由（呼ばなかった神と理由も含む）は軌跡に記録する。

### 招集パターン

| パターン | 内容 | 使いどころ |
|---------|------|-----------|
| 逐次 | 前の出力を次が参照 | 依存関係が明確な時 |
| 部分並列 | 独立した神は並列 | 時間制約がある時 |
| 完全並列 | 同じ問いを独立視点で | 総合視点が必要な時 |

## 自律度レベル

| レベル | 名称 | 人間介入 | 使用場面 |
|--------|------|---------|---------|
| L1 | Collection | 各フェーズ後に判断 | 仕様未確定・未知技術 |
| L2 | Deliberation | 収束後に確認のみ | 仕様確定後 |
| L2.5 | 先行モード | 推論で進めてみる（実行済み時制） | 方針提示後の実装 |

L2.5の詳細は後述。

## L2.5 先行モード（PhronisisCode版）

### 本質

根本さんの「俺待ちを減らす」ためのモード。Kaiが判断OSに照らして推論で進め、実行済みとして事後報告する。

### 動作原理（本家からの継承・簡略化）

1. Kaiが判断OSに照らしてタスクを進める
2. 高確信（70%以上）→ 簡略化して進める。自己検証1回 + 軌跡に省略理由
3. 低確信（70%未満）→ 深層思考/Yuna/Hayatoで「根本さんならどうするか」を導いてから進める
4. 三者統合: Kaiが判断OSに最も忠実な案を選ぶ
5. 実行は実行済み前提。事後報告を行う

### Hayatoゲート（コーディング特化・オーバーキル回避）

Hayatoゲートは「手続き検証 + 致命傷検出」に絞る。スタイル・好みは射程外（Metisの領域）。

**判定観点（4点。機械判定でチェック）:**

1. 仕様逸脱: `tasks/{id}/brief.md` の成功基準（必須項目）がコードで満たされていること。満たされていない必須が1つでもあれば FAIL
2. バグ・セキュリティ致命傷: クラッシュ・データ破損・XSS/SQLi・権限昇格等の致命傷がないこと。該当コードがあれば FAIL。ロジック誤り・性能劣化は Metis/Daedalus の指摘を経由して FAIL に昇格する
3. 手続き違反: 宣言と実体の不一致（L2.5の手続きを守ったか）。brief/plan/log の必須ファイルが欠落、または招集判断の記録がない場合は FAIL
4. 軌跡の品質: `tasks/{id}/brief.md` の軌跡表（論点/選んだ案/潰した案/理由）の4列が非空であること。空欄があれば FAIL。中身の良し悪しは Metis が見る

- 判定は上記バイナリ照合で行い、Hayatoの主観で観点を広げない。想定外の穴はチェックリスト外でも「仕様逸脱」または「致命傷」に該当すれば刺せるが、スタイルの好みで FAIL にしない
- 発動タイミング: 中間軽量チェック（5行以内）+ 最終手続き検証（完結時）の2回のみ。常時ループはしない
- 必須実行: `python scripts/code_health_check.py --no-color` が exit 0 であることを必須とする。失敗時は Hayatoゲート観点2（致命傷）に該当し BLOCK とする

- 3ゲート可視化:

  | Hook | タイミング | チェック | 失敗時 |
  |------|-----------|---------|--------|
  | pre-commit | commit時 | `hooks/utf8_check.py`（UTF-8破損） | BLOCK |
  | pre-push | push時 | `hooks/handover_check.py`（handover整合性） | BLOCK |
  | pre-push | push時 | `scripts/code_health_check.py --no-color`（5検査） | BLOCK |

**ループ制御（大局観維持・近視眼防止）:**

- 修正ループ上限: 3回（再アンカーを含む。除外なし）
- 2ループ目に深層思考で仕様（brief.md）へ再アンカー + Yunaプリズム照合を1回挟む（近視眼化防止。ループはカウントするが、再アンカー自体は「実装を止めて仕様に立ち返る」行為として扱う）
- 再アンカーの問いは「この修正は brief の成功基準に忠実か。大局観を見失っていないか」。再アンカー後は必ず軌跡に「再アンカーで何を見直したか」を1行残す
- 3回で通らなければ Hayato が BLOCK を維持したまま停止。Kai は `tasks/{id}/log.md` に `status: blocked` を残し、チャットで根本さんにエスカレーションする。エスカレーションは致命傷（観点1-3の FAIL）が残る場合のみ。軽微な残課題（観点4のみ WARN）は Kai が自律で決めて報告に「軽微な残課題として自律確定した」と明記する
- 完了宣言は Hayato PASS または WARN の時のみ可。BLOCK のまま自律確定してはならない

**fast-path（軽微タスクの端折り防止）:**

- 1ファイル・5行以内・仕様変更なしの軽微修正は、brief 1行 + トライアングル簡略1往復（深層思考+Yuna/Hayato 軽量）で可とする。但し招集判断で「呼ばなかった理由」を1行残すことは省略しない。軽微だからと軌跡を端折ってはならない

### 収束後フロー

1. 実行結果を報告。末尾に **【自律実行】推論で進め、実装まで行いました。確認してください。違和感があれば差し戻しをお願いします（24時間以内）。** と明記
2. 成果物には判断の軌跡（3行）を添付。低確信で相談ループを回した場合は相談ログも含める
3. 根本さんの確認:
   - 明示的「OK」→ 確定
   - 何も言わない・別話題 → 未確定のまま保持。次回セッションで確認
   - 「止めて」→ 手動承認待ち
4. 異議があれば該当論点のみL2にフォールバック

### 使用制限

- 倫理的一貫性に懸念がある場合はL2にフォールバック
- 破壊的操作（git履歴書き換え・force push等）を含む局面では事前承認を必須とする。推測で進めない

## 完了宣言の定義

完了宣言は「内容検証（自己検証80%以上）」と「手続き検証（Hayatoゲート PASS/WARN）」の両方を満たして成立する。
「作成した」「実装した」だけでは完了宣言にならない。

### 自己検証80%の定義

80%とは `tasks/{id}/brief.md` の成功基準（必須項目）に対するテスト/手動確認の通過率を指す。
例: 必須5項目のうち4項目がテストまたは手動実行で確認できれば80%。Daedalus が呼ばれなかった場合も Kai が `tasks/{id}/log.md` に「何をどう確認したか」を記載し、Hayato が観点1（仕様逸脱）で検証する。自己申告の「80%です」だけでは通過しない。

## 深層思考の運用

深層思考はKai自身に適用する認知モードである。

- 起動条件: 発散が必要な時、行き詰まり検出時、創作・転換が必要な時、根本さんから明示指示時
- 手順: 深層思考で再考 → `tasks/{id}/deep_thought.md` に出力 → 必要に応じて神々に委任
- 禁止: 常時適用しない。定型的な実装レビューでは不要
